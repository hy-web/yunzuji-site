## 一本公开的家族活动记录册

理清"谁和谁是什么关系"只是家族管理的一半。一个家族在长期运转中，还会沉淀大量**事务性内容**：

- 红白喜事、祭祖、聚会的纪事与通知
- 长辈口述、老照片、活动影像
- 祠堂修缮、族谱编修等公共开支与份子钱的来龙去脉
- 需要让每个人都看到、并能确认"大家都看过"的事情

这些不适合塞进族谱的关系结构里，云族记把它们独立成「家族事务」模块，与「人际关系」并列。

它的定位很明确：**一本对全家族公开的活动记录册，而不是一套通知 / 审批系统**。现实里家族活动的钱常在微信群里收发、由长辈在纸上记账，其他成员并不知道纸上写了什么。这个模块要做的，就是把这些记录公开沉淀下来——纪念一场活动，仅此而已。因此它**不做**通知范围圈选、不做选人推送、不做报销审批流。

## 模块边界

```
云族记（家族管理应用）
├── 人际关系模块            记录"谁是谁"——关系网络、称呼、身份、权限
│      └── 详见 人际关系画布 / 称呼引擎 / 权限模型
└── 家族事务模块（本页）     记录"发生了什么"——活动纪事、照片、收支
       └── 与族谱关系数据相互独立，不影响关系结构
```

两个模块共享同一套账号、家族与权限体系（谁是本族人、谁是管理员、谁有访问权），但**数据各自独立**：删掉一条事务记录不会影响族谱，整理族谱也不会动到纪事。

## 一条记录长什么样

家族事务在底部导航栏是独立的「**记录**」入口。底部导航共四个入口：**首页 / 记录 / 关系 / 我的**。

**记录列表**

- 分「在记 / 已存档」两段，按时间排列，进行中、需要关注的活动在前
- 管理员有发布入口，可对记录做编辑、存档、恢复，并查看已读；普通成员只浏览
- 点进一条记录，先看到一张"记录纸"

**一张记录纸（信纸）**

- 管理员在拟纸页发布：标题、一段正文、记录人（默认就是当前操作者）
- 成员打开是同一张纸的只读形态，从底部进入详情
- 用纸面而不是表单卡片，是为了贴合"家族纪事"的阅读感，也让长辈更容易把它当一本册子来看

**活动详情与照片**

- 一条记录下可以持续追加多条"进展"，每条一段文字、可附照片（最多 20 张）
- 照片以画廊形式浏览，便于沉淀老照片与活动影像
- 修改、删除详情时，对应的云端图片会被真正回收，不会留下无人引用的文件空占存储

**家族收支台账**

- 每条活动记录附带一本简单台账：区分**收入 / 支出**，记一笔**用途**和**金额**
- 管理员可以记账，也可以代成员填写
- 成员也能**自助登记自己的那一笔**（一人一笔、无需审批确认），登记人在后台留痕
- 刻意保持极简：不做会计科目、不做统计报表，只回答"这件事什么时候办、花了多少钱、钱去了哪里"

**已读与存档**

- 发布者能看到**谁看过**这条记录，重要通知不会"发了没人知道看没看"
- 过期活动可存档：存档后变为只读，但**仍然对全员可见**，相当于归入册尾；需要时还能一键恢复

## 角色与权限

- 每个家族只有**一名管理员**（建族账号），负责发布 / 编辑 / 存档、记账与代填
- 普通成员浏览记录、查看照片与台账，并可登记自己的那一笔收支
- 外族成员能否看到，沿用家族的开放档位与权限体系，与族谱模块一致
- 台账等写操作在数据库层禁止直连写入，统一由云函数在校验身份后执行，前端隐藏不是安全边界

## 设计取舍：刻意保持简单

这是一个"有需要才用、没需要就放着"的模块，而不是日常高频应用，所以功能边界收得很紧：

- 一名管理员，不设多角色、不做协作审批
- 一本台账只记收支、用途、金额，不做完整财务系统
- 不做通知选人、不做消息治理，公开即全员可见
- 信息简短易懂，优先照顾长辈的操作负担
